# Управление Human: команды движения и владение

Статический разбор установленного GOG EXE с SHA256, указанным в AGENTS.md.
Игра не запускалась, функций движка этот разбор не вызывает. Пользовательская
пауза тестов ради Cyberpunk сохраняется. Ни AI ownership, ни сетевое управление
движением этими результатами не подтверждены.

## Несовместимый пример из m2o-reborn

В upstream pedestrian.h для MoveDir выделяется 0x58 байт и вручную записывается
vtable **0x19661bc**. На нашем EXE это другая команда:

- slot 0 указывает на 0x953b80; этот deleting destructor вызывает обработку
  поля **this+0x78**, уже за пределами выделенных 0x58 байт;
- конструктор 0x953b30 тоже инициализирует поле +0x78;
- штатный путь 0x95ed6a выделяет для этого vtable **0x98** байт.

Не копировать эту комбинацию размера/vtable и последующий ручной delete.
Это подтверждённое несоответствие типов для нашего EXE, а не доказанный краш
upstream на всех поддерживаемых им изданиях.

Штатная MoveDir здесь имеет размер **0x58**, vtable **0x18f14b0**, deleting
destructor **0x42d3e0**. Это видно в двух независимых путях: создании команд
0x95b0f0 и инициализации игрока около 0x42fa7b. Не путать адрес 0x42d3e0
с функциями очереди в диапазоне 0x94d3xx.

## Найденный штатный путь создания

Кандидат 0x95b0f0 принимает Human в ECX и два аргумента стека:
`out_ref` (адрес четырёхбайтового intrusive smart pointer), затем тип команды.
Возвращает адрес `out_ref`, очищает восемь байт аргументов. Это не функция,
которая возвращает сырой Command в EAX.

Тип 1 выделяет MoveDir 0x58, задаёт правильный vtable, нулевой refcount +4
и часть исходных полей, создаёт временную ссылку, вызывает AddCommand,
затем конструирует дополнительную ссылку в out_ref. Тип 0 создаёт Stand 0x20.
Другие типы в этом пути не создаются.

**Не включено в observer:** фактический вызов и ошибка выделения ещё не проверены.
В видимом пути null allocation всё равно доходит до AddCommand с null-командой,
а type-1 initializer её разыменовывает. Этот путь нельзя объявлять безопасным
при отказе памяти. Также до вызова нужно проверить свободный слот очереди.

## Ссылки и ABI AddCommand

0x94d400 — thiscall, два аргумента и ret 8. Для type 1 jump table ведёт
в 0x94d428, далее initializer 0x936fb0 и insertion 0x94d320.
Последний через 0x429a30 сохраняет **удерживаемую ссылку**, а в конце AddCommand
0x422db0 уничтожает ссылку аргумента. Представление аргумента в стеке выглядит
как указатель, но его передача имеет семантику smart pointer по значению.

0x4237b0 увеличивает Command+4; 0x422db0 уменьшает его, при нуле вызывает
vtable[0](1). Assignment 0x429a30 сначала удерживает новый объект, затем
отпускает старый, включая deleting destructor при нуле.

Ожидаемый баланс штатного успешного CreateSimpleCommand: новый refcount 0,
временный аргумент +1, очередь +1, уничтожение аргумента -1, out_ref +1:
**одна ссылка очереди и одна ссылка вызывающего**. Это статически выведенный
баланс; наблюдение счётчиков и проверка очистки в игре ещё впереди.
Не освобождать raw Command через delete/Free после engine cleanup.
Живой refcount также не доказывает, что команда всё ещё стоит в очереди.

## Очередь — не массив приоритетов для ручной записи

Из инициализации 0x916e30, insertion 0x94d320 и удаления 0x94d390 следует:

| Поле Human | Назначение в разобранном коде |
| --- | --- |
| +0x138 + slot*8 | Удерживаемый указатель команды, 8 слотов |
| +0x13c + slot*8 | Индекс следующего слота в связном списке |
| +0x178 + queue*4 | Головы пяти очередей |
| +0x18c | Голова списка свободных слотов |

В начале ссылки свободных слотов идут 0→1→…→7→-1, free_head=0,
головы очередей равны -1. Insertion снимает свободный слот, дописывает его
в хвост нужной очереди и ставит бит 0x400 в Command+0x0c.
Removal очищает ссылку и возвращает слот в свободный список.

Имя SDK `m_iNextCommand` для +0x18c вводит в заблуждение. Прямая запись 1
в +0x18c и `m_aCommandsArray[1].m_pCommand` из upstream обходит и повреждает
владение/связи. Не использовать её для выбора текущей команды.
Перед будущим enqueue проверять диапазоны -1/0..7, отсутствие циклов/пересечений,
правильный free_head и наличие свободного слота. Проверять registry identity
Human и выполнять движковые изменения только на его игровом callback.

Initializer MoveDir задаёт type 1 в младшем байте +0x0c, descriptor +8,
несколько defaults и маски старших битов +0x50. +0x50 не просто независимый
байт скорости: старшие биты используются отдельно. Сетевой адаптер должен
менять только подтверждённые поля, не обнулять весь DWORD по имени из SDK.

## Воспроизведение статического разбора

```powershell
python scripts/audit_human_commands.py '<game>/pc/mafia2.exe' --output work/human-commands.json
```

Скрипт сначала сверяет полный SHA256, затем ограниченные участки PE с точными
байтами. Он не публикует бинарник/дамп и всегда оставляет
`runtime_control_verified=false`, `ai_ownership_verified=false` и
`allocation_failure_recovery_verified=false`.

## Нативная проверка очереди перед будущим управлением

Добавлены `src/game/command_queue.c/h` и `CoopReadCommandQueue`. Читатель требует
от вызывающего проверенного registry handle, нужную сборку EXE и игровой поток.
Он сам не разрешает движковые вызовы. Его ограниченный снимок +0x138..+0x190
проверяет все индексы, достижимость восьми слотов ровно в одном из шести списков
(пять очередей и free list), отсутствие циклов/пересечений/потерянных слотов.
Свободный слот должен иметь null reference; занятый — читаемый выровненный
Command header с положительным signed refcount и выставленным engine битом 0x400.
Ненулевой выровненный vtable здесь не доказывает класс/исполняемость его методов.

После чтения headers исходные 0x58 байт читаются снова; изменение означает
отдельный неуспех. Это обнаружение изменения, а не атомарный снимок или
разрешение читать/менять команды с network thread. При любом неуспехе выходной
снимок остаётся нулевым, его указатели/счётчики использовать нельзя.

Дополнительно читается отдельная удерживаемая ссылка Human+0x1a0 и её header.
Она может существовать вне очередей с уже очищенным битом 0x400 — это не ошибка
топологии. `retained_is_queued` сообщает только наличие того же указателя среди
занятых слотов, а не факт текущего исполнения. Ссылка +0x1a0 тоже перечитывается
для обнаружения изменения. Прочитанный положительный refcount не даёт читателю
владение этой ссылкой и права позднее использовать сохранённый указатель.

Статусы: 0 unreadable, 1 corrupt topology, 2 bad reference/header,
3 changed snapshot, 4 valid layout. **Valid с free_count=0 означает заполненную
очередь**, а не возможность вставки. Проверка не определяет владение AI,
не отменяет чужие команды и не доказывает, что допустим конкретный enqueue.

В существующий явно включаемый `-TestHuman` добавлены только наблюдения очереди
после активации и спустя пять секунд: `command_queue_status`, а при valid —
число свободных/занятых слотов. Перед ними заново разрешается GUID Human.
Теперь также записываются наличие retained reference, её присутствие в очередях
и наблюдаемый dispatch skip flag; адреса в этих строках не выводятся.
Новых вызовов команд/изменений очереди нет; сетевое управление не включено.

Полная pinned сборка прошла с warnings-as-errors. Fixture `test_command_queue.c`
написан и скомпилирован, но **не исполнен** из-за пользовательской паузы тестов.
Проверки предполагают пустую/полную очередь, циклы, пересечения, orphan slots,
неверные индексы/ссылки, нечитаемую память и изменившийся снимок. Это план
проверок, не утверждение об их прохождении. Игровых результатов этой версии нет.

## Диспетчер, завершение и отдельная ссылка на движение

Human vtable+0xc8 указывает на 0x9818a0. Он вызывает 0x94d9a0 с float-аргументом,
если Human+0x20 не содержит 0x200000. Этот бит пропускает также соседний вызов
работы с физикой; его нельзя объявлять способом «выключить только AI».

0x94d9a0 делает два прохода по пяти очередям. В первом он вызывает функцию из
Command descriptor+0 через Human+descriptor[+4], если нет флага 0x200 в +0x0c;
для очереди 0 передаёт ранее удерживаемую ссылку +0x1a0. Флаг 0x800 прекращает
дальнейший проход текущей цепочки. Это подтверждённые ветвления; полную семантику
флагов и правил AI-приоритета ещё нужно разбирать.

Во втором проходе вызывается descriptor+8 с Human adjustment из descriptor+0xc,
командой и float-аргументом. False приводит к снятию головы, очистке 0x400,
отпусканию ссылки очереди и возврату слота в free list. True для очереди 0
сохраняет дополнительную ссылку в **Human+0x1a0** через intrusive assignment.
Getter 0x94d540 читает голову очереди 0; он не читает эту отдельную ссылку.

Кандидат ClearMove 0x94d8d0 отмечает команды очереди 0 битом 0x100,
вызывает доступный descriptor callback+0x10 через adjustment+0x14, снимает
ссылки/возвращает слоты и вызывает physics vtable+0x14. Он **не очищает +0x1a0**.
Общий ClearCommands 0x94d6b0 очищает эту ссылку при ненулевом первом аргументе;
дополнительные ветви влияют и на физические callback handles.
Эти функции пока не вызываются новым кодом.

Следовательно, нельзя приравнивать «ссылки нет в очереди», «команда уничтожена»,
«физическое движение остановилось» и «AI потерял управление». Для disconnect,
паузы и unload будущего remote adapter нужны отдельные проверки этих состояний.
Отключение AI, вызовы остановки и фактический эффект в игре пока не подтверждены.

SDK `C_AIController::NewCommand(void*)` (0xf9f880) также не является альтернативой
для передачи сырого MoveDir: в разобранной ветви он читает два слова аргумента
и разыменовывает второе как адрес отдельного счётчика. У MoveDir второе слово —
сам числовой intrusive refcount. Передача raw Command под этой void*-сигнатурой
не соответствует машинному контракту. Точный тип AI payload/владение им и способ
отмены AI-задач ещё не установлены.

Следующий шаг без игровых тестов: разобрать источники AI/скриптовых команд,
владение ими и правила прерывания. После разрешения тестов нужны проверки создания,
движения/остановки, отмены AI-команд, удержания/отпускания ссылок и unload.
Обычный SetPosition и существующий локальный Human ещё не дают управляемого
сетевого аватара или совместного прохождения сюжетной миссии.
